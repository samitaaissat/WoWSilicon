# WoWSilicon 3.0.0 — Metal, end to end

This is one release that folds in everything built since 2.5.5. WoWSilicon now ships its own Wine, its own Direct3D 9 → Metal renderer, and its own x87 JIT, so there is no CrossOver purchase, no CrossOver install, and no CrossOver patching step anywhere in the flow. Download one app, pick your game folder, apply the Game Patch, press Play.

## Metal-native rendering

Options → General opens with a **Renderer** picker, set per game version:

- **mtld3d (Metal, recommended)** — [athei/mtld3d](https://github.com/athei/mtld3d), a Direct3D 9 implementation written directly against Metal. No Vulkan hop, no MoltenVK. It is the default for new installs and needs no setup: the app stages the right `d3d9.dll` beside the game and the matching builtins ship inside the bundled Wine.
- **d9mt (Metal, experimental)** — the other D3D9 → Metal path, kept as an alternative. It compiles shaders at runtime, so selecting it requires the Xcode command line tools; if they are missing, the app tells you to run `xcode-select --install` instead of failing later.
- **d9vk (Vulkan, legacy)** — DXVK's D3D9 over Vulkan and MoltenVK, the long-serving fallback.

Changing the renderer re-applies the game patch for you so the right files are staged before the next launch. The change takes effect the next time the game starts, and the switch is refused while a patch operation is already running. The Game Patch status row is renderer-aware and will say the staged `d3d9.dll` is outdated when it no longer matches your selection.

**Limitations worth knowing before you switch:**

- **Neither Metal renderer supports multisampling, and the app does not turn it off for you.** In WoWSilicon's Graphics options the control is called **Anti-Aliasing**, and it still defaults to 2x. Under mtld3d the missing capability is reported honestly and the game falls back cleanly. Under d9mt it does not: leave anti-aliasing on and **the screen renders black**. Set Anti-Aliasing to Off in WoWSilicon *and* Multisampling to Off in the game's own video options before using d9mt.
- **Under mtld3d, fullscreen never changes your display mode.** mtld3d presents into a borderless window covering the monitor, which means the resolution chosen in the game's video options has no effect in fullscreen or in a maximized window. The render resolution knob is `render.scale` in `mtld3d.conf`, staged next to your game executable: values from just above 0 to 1.0 rasterize on a smaller grid and let MetalFX upscale on the way to the screen. 0.75 is a good first try; 0.5 renders a quarter of the pixels and looks noticeably soft, because the UI and text scale too. Values above 1.0 are rejected, and on a GPU without MetalFX the scale stays at 1.0.
- `mtld3d.conf` is a heavily commented sample file covering HDR, colour space, shader cache, an FPS cap, memory limits, `render.scale` and `cursor.scale`. It is only written if no file is there, so your edits are never overwritten — but note that removing the game patch deletes it, so keep a copy of a hand-tuned config.

d9mt also received a correctness and performance pass in this release: projected ground textures (spell decals, blob shadows) no longer z-fight the terrain as stripes, render-target round-trips and the per-draw bind path are faster, and d9mt now reports the same Apple GPU identity d9vk does, so the game takes the same vendor-specific code paths.

The Cursor Size option now works under the default renderer: it writes `cursor.scale` for mtld3d as well as the dxvk setting for d9vk, so the choice survives a renderer switch. d9mt has no cursor-scaling knob, so the setting has no effect there.

## WoWSilicon ships its own Wine — CrossOver is no longer required

The CrossOver row, path picker, patch and unpatch buttons and version gate are all gone from the dashboard. In their place there is a single **Runtime:** status line that stays quiet unless the bundled runtime is missing.

- The bundled runtime is a pre-patched Wine 11.15 built from `WineAndAqua/wine` (branch `wine-11.15-macos`), shipped as runtime v4. It is a slim, game-focused build: Vulkan/MoltenVK, CoreAudio, freetype, gnutls and SDL, with no X11, OpenGL, GStreamer, PulseAudio or dbus. The libraries it loads for rendering, fonts and TLS — MoltenVK, freetype, gnutls and their dependency closure — are bundled inside the runtime and re-pointed at it, so the graphics stack does not depend on Homebrew being installed on your Mac. Wine's LGPL license texts ship inside the app.
- **The runtime updates itself in the background.** Once per launch (and at most once a day) the app checks for a newer Wine runtime or renderer payload, verifies every download against its published checksum, and assembles it into a copy alongside your data — never inside the signed app bundle. Wine and renderer fixes therefore reach you without waiting for an app release. Troubleshooting has a **Check for Runtime Updates** button and shows whether you are running the copy inside the app or a downloaded update. There is no opt-out switch; the check is a plain HTTPS request to GitHub.
- A downloaded runtime that is missing anything this build needs is refused outright and the app falls back to the copy inside itself, rather than being used and failing deep inside the game's loader.
- **Crashes are reportable now.** The runtime ships `winedbg`, so a crash prints the faulting thread, backtrace, module list and registers instead of the old "Couldn't start debugger" dead end — and the build fails outright if `winedbg` ever goes missing again.
- **Every play session is logged** to `WoWSilicon Data/Logs/wine-session-<timestamp>.log`: the whole session, including the Wine server's own messages (often the only record of why a client died) and the real exit status. The ten newest are kept and older ones pruned; only WoWSilicon's own log files are ever touched. There is no button for these in the app — open the Logs folder yourself when you want to attach one to a report. If the app is running from a read-only place like the DMG, the session simply goes unlogged rather than refusing to launch.
- **New: Enable MSync (experimental)** in Options. Wine's faster synchronization primitive, off by default, because some applications break under it. It takes effect on the next launch, and toggling it shuts the Wine server down cleanly first (never during a live session) so the next launch starts in agreement with it.
- CrossOver survives only as a Troubleshooting action — **Restore CrossOver Modifications** — which undoes what WoWSilicon 2.x did to a CrossOver install. WoWSilicon never touches CrossOver otherwise.

## x87sidecar: the JIT moved out of the game

The x87 floating-point JIT that makes these clients playable under Rosetta is now [athei/x87sidecar](https://github.com/athei/x87sidecar), running as a **separate process** that the game attaches to cooperatively — Wine hands over its task and thread control ports voluntarily at startup, with a matching handshake patch in the bundled runtime.

- Cooperative attach needs no debugger entitlement, so the macOS authorization prompt the old injected JIT required on first launch is gone.
- Because the JIT's code never lives inside the game's address space, the whole class of failures where a signal landing in injected code aborted the process (`rosetta error: no code fragment associated with the given arm pc`) is structurally impossible now.
- **Nothing x87-related is written into your game folder any more.** Applying (or removing) the game patch deletes the leftover `rosettax87/` directory that 2.x created.
- The sidecar ships inside the Wine runtime and versions with it, so it rides the same background, checksum-verified self-update. This build pins runtime v4 with x87sidecar v1.5.0.
- Acceleration is unconditional: every renderer and every launch path runs under the sidecar, and there is nothing to configure. Troubleshooting reports its status, and if it is ever missing the app says so plainly instead of surfacing a confusing Wine error.

## Portable by design — and your settings stop resetting

Everything mutable now lives in a single **`WoWSilicon Data`** folder created beside the app: the Wine environment, `versions.json`, `prefs.json`, session logs and downloaded runtime updates. Copy the app and that folder together and your entire installation moves — to another folder, an external drive, or a different Mac. Nothing about the location is written down anywhere; the app re-resolves it from wherever it is launched. The folder gets an `About this folder.txt` explaining exactly that.

- **WoWSilicon now has its own private Wine environment and never touches `~/.wine`.** This is the fix for "my settings randomly reset": 2.5.5 launched with no prefix set at all, so the game landed in the shared global `~/.wine` that CrossOver, GameHub and anything else Wine on your Mac co-own and churn. Every single Wine invocation now pins WoWSilicon's own environment, and it is pinned last on the command line so a `WINEPREFIX` typed into the custom environment variables field can no longer redirect the game away from it.
- **First launch sets up the Wine environment as a visible step**, with "Setting up the Wine environment — the first run can take a few minutes" instead of a window that looks frozen. Launch, Apply Patch, Install Visual C++, Install Launcher, Option-as-Alt and High Resolution Mode all wait for it and then run by themselves, instead of racing it or silently doing nothing. A failed or timed-out setup deletes the half-built environment so the next attempt starts clean.
- **Running from the DMG works.** If the app is launched from a read-only or quarantined location, it quietly uses `~/Library/Application Support/WoWSilicon` instead — a normal state, not an error. Once you drag the app somewhere writable, the next launch *moves* your existing environment into the portable folder rather than rebuilding it — a plain rename on the same disk, and across disks a staging copy that is verified before an atomic rename, so an interrupted move can never leave a half-copied environment behind.
- **Your existing settings are copied in on first run**, not moved: `versions.json`, `prefs.json` and the legacy `version_manager.json` are copied byte-for-byte out of Application Support, leaving the originals intact as a rollback net.
- **Cloud-synced folders can't corrupt your Wine environment.** If the Data folder lands somewhere that cannot safely host one — iCloud Drive, Dropbox and friends, or a volume without symlink support — your settings stay portable and only the Wine environment falls back to Application Support. Troubleshooting says so explicitly.
- The Wine environment is excluded from Time Machine, so backups no longer churn on it.
- **Troubleshooting was rebuilt around all this.** It shows which storage location is active and why, the bundled Wine version and whether it is the built-in or a downloaded copy, and the x87 loader's status. **Reset Wine Prefix** deletes only WoWSilicon's own environment; **Reset WoWSilicon (delete all data)** clears the Data folder (plus the Application Support fallback copy when you are running portable); both refuse to run while Wine is still alive and tell you to quit the game first. Deleting the legacy `~/.wine` is a separate, explicitly confirmed action — it removes `~/.wine` and a `.wine` directory inside your game folder, and carries a warning that `~/.wine` is shared with other Wine software. The copyable debug log now includes the active renderer, the storage location, the data and prefix paths, and whether a legacy `~/.wine` is still hanging around.

## macOS Game Mode and performance

The bundled runtime is staged as a nested application bundle so that macOS recognizes the game process as an actual game rather than an anonymous helper, granting it Game Mode's prioritized CPU and GPU access and doubling the Bluetooth sampling rate for wireless controllers and AirPods. Game Mode engages the usual way: the game window has to be frontmost and cover the screen — set Fullscreen in the graphics options. A small internal shim keeps that identity across Wine's re-exec into the 32-bit loader and through x87sidecar, the step that previously lost it, so there is nothing for you to configure. (One consequence: don't move, rename or re-sign anything inside the app bundle by hand.)

**App updates no longer force a multi-minute Wine rebuild.** Wine re-runs a full environment refresh whenever its own timestamps disagree, and the way the runtime used to be copied at build time restamped them on every single build — so every app update dragged users through a pointless refresh. Timestamps are now preserved end to end into the shipped DMG, and a refresh happens exactly once, on a genuine Wine runtime bump.

## Other improvements

- Option-as-Alt, High Resolution Mode, the Microsoft Visual C++ runtime installer and vanilla-tweaks all run on the bundled runtime against WoWSilicon's own environment. The "CrossOver wineloader not found" errors they used to raise are gone.
- Third-party launcher executables (the Electron-based ones) now actually render under the bundled runtime: the CrossOver-era Chromium flags produced either no window at all or a permanently blank one, and the launcher is now pinned to a software-rendered ANGLE path that draws correctly.
- **Force Quit is scoped to WoWSilicon.** It used to match every Wine process on the machine and hard-kill them, taking CrossOver and any other launcher down with it. It now asks WoWSilicon's own Wine server to shut down cleanly first — which flushes the registry — waits, and only then escalates against WoWSilicon's own binaries and a wedged JIT helper. The old behaviour discarded up to 30 seconds of unsaved settings, which is another way prefixes appeared to reset themselves.
- Game folders and custom environment variables containing spaces, dollar signs, backticks or backslashes now launch correctly; previously they were pasted into the shell unescaped.
- **Downgrading the app can no longer wipe your game list.** An unrecognized renderer name in the settings file now falls back to the default instead of failing the whole decode and resetting your configured versions.
- Opt-in telemetry now reports the renderer you are actually using instead of always saying d9vk. Nothing else about telemetry changed — it is still opt-in, off by default, and collects the same coarse fields.
- The addon manager, mod manager, realmlist editor, graphics options and Sparkle app auto-updates are unchanged from the 2.5.x line and work exactly as before.

## Fixes

- **Games no longer close for no reason.** This is the biggest stability fix in the release. Sessions could simply end — no Wine message, no error dump, no macOS crash report — and sometimes the process would limp on visibly degraded. The cause was in Wine itself: its fault handler assumed every thread in the process was one Wine created, but the Metal renderers bring Metal and libdispatch callback threads into the process. A fault on one of those made the handler fault again while handling the first fault, and the thread died in total silence. The bundled runtime now detects a thread Wine did not create and steps aside, so macOS writes a real crash report naming the actual faulting frame — and with `winedbg` and session logs, that crash can be reported without reproducing it.
- **d9mt: striped z-fighting on ground decals is fixed.** Spell decals and blob shadows fought the terrain because the renderer was forwarding the depth-bias value to Metal in the wrong units, arriving effectively as zero.
- **A background runtime update can no longer leave the app unable to start the game.** A downloaded runtime assembled by an older app build could be missing files this build needs, producing a launch failure deep in the game's loader — and it could stay that way for a day, because the update check runs at most once every 24 hours. The downloaded runtime is now inspected for those files on *every* launch: if anything this build depends on is absent, the app runs from the copy inside itself instead, and the stale download is rebuilt or discarded on the same pass.
- **Clicking Launch or Patch during first-run setup no longer silently does nothing.** Those clicks are queued and run once setup finishes, with the progress banner restored.
- Troubleshooting's destructive actions refuse to run while the game is open, instead of racing a live registry flush.
- An interrupted move to an external drive can no longer leave a half-copied Wine environment; leftovers from a crashed attempt are cleaned up on the next launch.
- The game no longer refuses to start over a mismatched msync or Wine server setting — both are now pinned explicitly on every launch.

## Upgrading from 2.5.x

- **You do not need CrossOver any more.** You can leave it installed for other software; WoWSilicon will not touch it. If you want to undo what WoWSilicon 2.x did to your CrossOver install, use **Restore CrossOver Modifications** in Troubleshooting.
- Your old `~/.wine` prefix is left completely untouched. WoWSilicon runs in its own private environment now, so nothing carries over from it automatically. When you are sure you no longer need it, Troubleshooting has a separate, confirmation-gated button to delete it — read its warning first, because `~/.wine` is shared with other Wine software.
- Because settings now live in WoWSilicon's own environment, **re-enable High Resolution Mode and reinstall the Microsoft Visual C++ runtime once** after upgrading. Option-as-Alt is re-applied for you automatically.
- Your settings files are copied into the new `WoWSilicon Data` folder on first run; the originals stay where they were.
- New installs and installs coming straight from 2.5.5 land on **mtld3d**. If you ran one of the interim 3.x builds, your stored renderer choice is preserved — which for most people means **d9vk** — so open Options → General and switch to mtld3d by hand to get the recommended path. The short-lived `wined3d` option is gone; anyone who had selected it is moved to mtld3d automatically.
- Before your first launch on either Metal renderer, check the Anti-Aliasing setting in the Graphics options. See the limitations above; on d9mt, leaving it on gives you a black screen.

As always, drag it into your Applications directory and run:

```sh
xattr -cr /Applications/WoWSilicon.app
```

Supported versions: macOS 15, macOS 26, macOS 27 (Apple Silicon)
